# ChipLoom over the Model Context Protocol

`chiploom mcp` is an optional adapter that exposes ChipLoom's command line as Model Context Protocol (MCP) tools over standard input and output. It exists for agents whose host speaks MCP and cannot (or should not) run shell commands. Agents with a terminal, such as Codex or Hermes, can keep calling the CLI directly: nothing requires MCP, and every tool here is a `chiploom` command with the same JSON contract (see [CLI.md](CLI.md)).

```sh
python -m tracker4agents mcp [--root DIR]      # or: chiploom mcp [--root DIR]
```

The adapter is part of the standard-library core: no MCP SDK, no Qt and no agent provider is needed to run it, and it is not an HTTP server.

## What it is, precisely

- **Transport:** stdio only. JSON-RPC 2.0, one message per line, UTF-8, `\n` separators. Nothing else is ever written to standard output; standard error stays empty in normal use.
- **Protocol versions:** `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05`, negotiated in `initialize` (a client that asks for another version is answered with `2025-11-25`). The stateless `2026-07-28` revision and its `server/discover` probe are not implemented; a client that probes answers `-32601` and falls back to `initialize`, which the official SDK does.
- **Capabilities:** `tools` only (`listChanged: false`). No resources, prompts, logging, sampling, progress or cancellation. Requests are handled one at a time, in order.
- **Implemented methods:** `initialize`, `notifications/initialized` (and any other notification, ignored), `ping`, `tools/list`, `tools/call`.
- **CLI-backed tools:** each call runs the matching command in a child process (`python -m tracker4agents ...` with the server's interpreter) and returns the command's JSON exactly. It arrives twice: as `structuredContent` and as pretty-printed JSON text. Tools declare an `inputSchema` but no `outputSchema`; results are the CLI's payloads, documented in [CLI.md](CLI.md).
- **Errors:**
  - A command that fails gives a normal result with `isError: true`, and the CLI's own `code` and `message` (for example `NOTE_UNKNOWN`, `LIVE_CONFLICT`) in `structuredContent`. Models can read it and correct themselves.
  - Arguments that do not match a tool's schema (unknown or missing keys, wrong types) also give `isError: true`, with `code: "INVALID_ARGUMENTS"`; the child process is not started.
  - An unknown tool name is a JSON-RPC protocol error (`-32602`); an unknown method is `-32601`; malformed JSON is `-32700`.
  - A command that runs longer than 600 seconds is stopped (`TIMEOUT`).
- **Annotations:** `readOnlyHint` is true for tools that only read, and `openWorldHint` is always false (everything is local). Tools that write do so to the paths you pass; they create new files rather than editing a source in place, except `live_patch`, `live_open`, `live_save` and the other `live_*` tools that act on the open session.
- **Paths:** relative paths are resolved against `--root` (default: the directory the server starts in). Give absolute paths when in doubt, and keep new work under `exports/<name>` as the repository instructions ask.
- **Patch operations:** `patch` and `live_patch` take the operation list inline in `ops`, or in `ops_file`, the path of a JSON file holding the same list (better for large generated patches); give exactly one. Channels, rows, patterns and orders count from 0 in operations and in every result (`changes` writes `ch0` for the first channel); sample slots count from 1.
- **Starting a song:** `new_project` writes a blank project (channel count, patterns, speed, BPM; library mode by default). `synth_palette` starts a song made only with created samples.
- **Composition policy:** by default compositions use only samples from the owner's local library: use the `samples_*` tools, record the library IDs and leave the PCM as it is. The `synth_*` tools are for songs the owner asks to be made only with created samples, and the `sample_*` (editing, drawing) and `instruments_*` tools are for when the owner asks you to shape a sound.

## Configuration

Use the interpreter of the environment where ChipLoom is installed (`pip install -e .` in the checkout). On Windows that is usually `<checkout>\.venv\Scripts\python.exe`; on Linux and macOS, `<checkout>/.venv/bin/python`. Absolute paths avoid depending on the client's working directory and `PATH`.

### Codex CLI

Verified with `codex-cli 0.155.1` (see [What was tested](#what-was-tested)). Either let Codex write the entry:

```powershell
codex mcp add chiploom -- "K:\Projects\tracker4agents\.venv\Scripts\python.exe" -m tracker4agents mcp --root "K:\Projects\tracker4agents"
```

or add this to `config.toml` in your Codex home (`~/.codex/config.toml`, or `%USERPROFILE%\.codex\config.toml` on Windows). Single-quoted TOML strings keep the backslashes literal:

```toml
[mcp_servers.chiploom]
command = 'K:\Projects\tracker4agents\.venv\Scripts\python.exe'
args = ["-m", "tracker4agents", "mcp", "--root", 'K:\Projects\tracker4agents']
cwd = 'K:\Projects\tracker4agents'
startup_timeout_sec = 30
tool_timeout_sec = 600     # renders and comparisons can outlast a short client timeout
env_vars = ["CHIPLOOM_HOME"]  # forward this variable from your shell, if you set it
```

On Linux or macOS use `command = '/path/to/checkout/.venv/bin/python'`. `codex mcp list` and `codex mcp get chiploom --json` show what Codex parsed; `codex mcp remove chiploom` deletes the entry. To try a configuration without touching your real one, point `CODEX_HOME` at an empty directory first.

### Claude Desktop, Claude Code and other `mcpServers` clients

Many clients read the same JSON shape (field names can vary). This is a generic configuration and **has not been tested with Claude Desktop, Claude Code or any other specific application**:

```json
{
  "mcpServers": {
    "chiploom": {
      "command": "K:\\Projects\\tracker4agents\\.venv\\Scripts\\python.exe",
      "args": ["-m", "tracker4agents", "mcp", "--root", "K:\\Projects\\tracker4agents"],
      "env": { "CHIPLOOM_HOME": "C:\\Users\\you\\AppData\\Local\\ChipLoom" }
    }
  }
}
```

Backslashes are doubled in JSON; forward slashes also work on Windows. Claude Code can also register a stdio server from the command line, `claude mcp add chiploom -- <python> -m tracker4agents mcp`, or from a project `.mcp.json` with the same `mcpServers` shape. Check your client's documentation for where the file lives and whether it asks you to approve the server.

### A generic stdio client

Any client that starts a stdio server needs only the command and arguments:

```text
<python> -m tracker4agents mcp [--root DIR]
```

with standard input and output connected to the client. A minimal session, one JSON object per line:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"demo","version":"1"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"estimate","arguments":{"orders":8,"bpm":160}}}
```

Closing standard input ends the server. The repository's own client, [`tools/mcp_smoke.py`](../tools/mcp_smoke.py), is a complete example with the official Python SDK.

## Compose together with the owner (live tools)

The `live_*` tools talk to a running ChipLoom window, or to a headless session you start from a terminal with `chiploom live serve SONG.json`. The adapter finds sessions through the discovery files under `CHIPLOOM_HOME` (default `%LOCALAPPDATA%\ChipLoom` on Windows, `$XDG_STATE_HOME/chiploom` or `~/.local/state/chiploom` elsewhere). If your client starts servers with a reduced environment, set `CHIPLOOM_HOME` explicitly to the same value the window uses. `live_sessions` never reveals the session token.

The collaboration rules are the ones from [the live reference](../skills/chiploom/references/live.md), in tool form:

1. `live_sessions`, then `live_status` and `live_score` to see what the owner has open. Remember the `revision`.
2. Read before you write: `live_changes` (use `since` with the last revision you saw) lists what the owner and any agent changed.
3. Make small edits with `live_patch` and **always pass `base_revision`**. Without it no conflict check happens and your edit lands on top of whatever is there. Keep the `revision` the result returns for your next edit.
4. If a patch comes back as an error with `code: "LIVE_CONFLICT"`, nothing was applied. The owner's edit wins: read `live_changes`, keep their work, adapt or drop your part, and resubmit with the new revision. Edits to other cells are not conflicts.
5. For a larger rewrite pass `propose: true` (without `base_revision`). The song stays unchanged until the owner accepts the proposal in the window. `live_proposals` shows its status (and whether it went `stale`); `live_withdraw` retracts it. After a rejection, ask what they want instead.
6. Give your agent its own `author` name, announce alternative versions as files with `live_take`, and use `live_select`, `live_play` and `live_stop` to show the owner a passage. `live_play` and `live_stop` return `LIVE_NO_WINDOW` on a headless session.
7. `live_save` without `output` writes the session's own project file; with `output` it writes a copy.

## Troubleshooting

- **The client says the server failed to start or closed immediately.** Run the exact command in a terminal: `<python> -m tracker4agents mcp`. It should wait silently for input. A `ModuleNotFoundError` means that interpreter does not have ChipLoom installed (`pip install -e .` in the checkout, or set `PYTHONPATH` to it).
- **Relative paths do not resolve.** They are relative to `--root`, not to the client's working directory. Pass `--root` or use absolute paths.
- **`live_*` reports `LIVE_NOT_RUNNING`.** No window or `live serve` answers. Open a song in the ChipLoom window (or start `live serve`), and make sure the client's environment resolves the same `CHIPLOOM_HOME` as the window.
- **A tool call times out in the client.** `render`, `preview` and `compare` can take a while. Raise the client's tool timeout (`tool_timeout_sec` in Codex). The adapter itself stops a command after 600 seconds.
- **`INVALID_ARGUMENTS`.** The arguments did not match the tool's schema; the message names the unknown or missing keys. Patch operations (`ops`) are validated by the CLI and fail with `PATCH_*` codes described in [CLI.md](CLI.md).
- **`render` fails.** Rendering needs FFmpeg with libopenmpt (or the optional xmp engine); the error says what is missing. Every other tool works without them.
- **Garbled non-ASCII text on Windows.** The adapter forces UTF-8 for its pipes and for the child processes. If a client passes text through a legacy code page before it reaches the server, switch that client to UTF-8.

## What was tested

Measured on Windows 11 with Python 3.14 for the client and the project's virtual environment for the server:

- **Official Python MCP SDK as a client.** `tools/mcp_smoke.py` launches `chiploom mcp` with the SDK's `stdio_client` and `ClientSession`, negotiates a protocol version, lists the tools, and calls `estimate`, `validate`, `inspect` (grid), `patch` (into a temporary copy), `report`, `synth_types`, and the live tools `live_sessions`, `live_status`, `live_score`, `live_patch` (with `base_revision`, including a refused stale patch and a proposal), `live_changes`, `live_proposals`, `live_withdraw` and `live_save` against a headless `chiploom live serve` in a temporary `CHIPLOOM_HOME`. It also checks error shapes and that standard error stays empty. It passes with `mcp` **2.3.0** (negotiated `2025-11-25`; its `server/discover` probe is answered `-32601` and it falls back to `initialize`) and with `mcp` **1.30.0** (negotiated `2025-11-25`). `tests/test_mcp_clients.py` runs it when `CHIPLOOM_MCP_CLIENT_PYTHON` points at an interpreter that has `mcp`, and the Core CI job does so on Linux and Windows with an SDK installed in a separate virtual environment. Without the variable the test is skipped; the SDK is not a project dependency.
- **Codex configuration.** With `codex-cli 0.155.1` and a temporary `CODEX_HOME` (the real `~/.codex` untouched): `codex mcp add chiploom --env CHIPLOOM_HOME=... -- <python> -m tracker4agents mcp --root <checkout>` wrote a `[mcp_servers.chiploom]` entry (`command`, `args` and an `[mcp_servers.chiploom.env]` table), and `codex mcp list`, `codex mcp get chiploom` and `codex mcp get chiploom --json` read it back as an enabled stdio server. The longer `config.toml` shown above (with `cwd`, `startup_timeout_sec`, `tool_timeout_sec` and `env_vars`) was written by hand into a second temporary `CODEX_HOME` and was accepted and reported the same way. That verifies the configuration format only: `codex exec` was not run.
- **Raw protocol.** `tests/test_mcp.py` drives the real child process over a pipe: handshake, listing, tool calls, error shapes, schema strictness, and that this document lists every tool.

**Not tested:** a model-driven session in any client (no model called ChipLoom tools through Codex, Claude Desktop, Claude Code or another application), the Claude Desktop and Claude Code configuration snippets, Codex starting the server and calling tools, other MCP SDKs, HTTP transports (not provided), and the stateless `2026-07-28` protocol revision (not implemented). Treat the configurations for those clients as starting points.
